# Prior art for agent handoff delivery

Research checked 2026-09-23. This evaluates whether existing systems can deliver a task to a specific, already connected agent and return a reliable result. It does not treat a shared inbox, an authenticated tool call, or a new model session as proof of that behavior.

| System | Documented mechanism worth studying | Boundary for AgentWay |
| --- | --- | --- |
| [OpenClaw Gateway hooks](https://docs.openclaw.ai/automation/cron-jobs/webhooks) and [ACP delivery](https://docs.openclaw.ai/tools/acp-agents/delivery) | Authenticated `/hooks/wake` can notify an agent's main session; `/hooks/agent` admits a turn with an idempotency key and separate completion/delivery facts. ACP bindings route follow-ups to a specific session; resume fails rather than silently creating a new session when the upstream session is missing. | This works because OpenClaw owns the gateway/session routing or a configured harness. It is not a universal ingress to arbitrary existing Muse, Grok Bot, or Codex desktop conversations. Its docs explicitly say mapped hooks are not durable exactly-once delivery. |
| [A2A protocol](https://a2a-protocol.org/latest/specification/) and [Microsoft Agent Framework A2A host](https://learn.microsoft.com/en-us/agent-framework/hosting/agent-to-agent) | Agent cards advertise capabilities and security. Messages have context IDs; tasks have lifecycle, cancellation, artifacts, polling, streaming, and callback updates. Microsoft provides adapters that expose agents under the host's control. | A2A requires the receiving agent to expose an endpoint or be hosted behind an adapter. A2A “push notifications” report task updates **from** the receiving server **to** its client; they do not wake an unrelated proprietary agent. Default Microsoft session/task stores are in-memory and explicitly development-only. |
| [MCP Agent Mail](https://github.com/Dicklesworthstone/mcp_agent_mail) | Identified agent mailboxes, threaded messages, acknowledgments, and searchable audit history. Its hooks remind an agent to read its inbox after other tool activity. | The recipient still calls `fetch_inbox`; reminders during tool use are not an unattended wake of an idle native agent. It is under active development. Study semantics, not code reuse without license review. |
| [LangSmith Agent Server](https://docs.langchain.com/langsmith/data-plane) and [Temporal](https://docs.temporal.io/workflow-execution) | Durable execution: persist work and state separately from a wake signal; workers recover after restart, and retries are visible. LangSmith uses PostgreSQL for runs and a Redis sentinel to wake its own workers. | These orchestrate workers/agents that the operator hosts. They solve AgentWay's delivery reliability layer, not the missing native ingress for each outside product. Bringing either runtime into the current app would need a separate scale/operational justification. |
| [Grok Bot collaboration](https://docs.x.ai/grok-bot/chat-and-collaboration) | Native asynchronous Bot-to-Bot messages show that a product can provide actual peer delivery and wake. | The documented operation is inside Grok Bot; no AgentWay-to-existing-Grok-Bot receiver route has been verified. |
| [MCP Tasks extension](https://tasks.extensions.modelcontextprotocol.io/specification/draft/tasks) | Client-started long-running tool calls can expose durable task IDs, progress and cancellation. | It is a draft extension for work a client already initiated; it does not supply unsolicited AgentWay-to-agent delivery. |

## Recommendation

The closest implementation pattern is **OpenClaw's explicit session binding and admitted-versus-completed-versus-delivered distinctions**, combined with **A2A's interoperable task/agent contract** and **LangSmith's separation of durable state from wake signals**. AgentWay's current SQLite task/inbox can remain the source of truth; do not adopt a full orchestration runtime simply to send a message. Add a delivery adapter only when the target product exposes a supported receiver for the exact user-owned agent/session. Such an adapter needs an authenticated target binding, stable idempotency key, acceptance receipt, asynchronous result, timeout and retry handling, and observable failure. A task marked `queued` is not `delivered`.

An A2A-facing endpoint may be useful for agents that can speak A2A, but it does not replace product-specific receiver integration. If the intended product cannot receive work while idle, it must not be advertised as a handoff recipient. Do not use a new OpenAI/Anthropic/xAI model session as a proxy for the user's existing native conversation without a separate explicit product decision. The next proof should be one end-to-end handoff between two real product connections, with no user relay, including recipient restart and duplicate-delivery tests. Then repeat the same contract for every advertised recipient, as required by [the delivery gate](handoff-delivery-gate.md).

The absence of a verified inbound route in the reviewed product docs is an evidence gap, not proof that the provider has no private or future API. Recheck official receiver capabilities before implementation.
