# Grok Bot webhook receiver adapter

Status: implementation branch `feat/grok-receiver-adapter`, 2026-09-24 UTC. This is one product-specific transport behind AgentWay's common automatic-delivery contract. It has **not** passed native receiver verification, does not mark any connection automatic-ready, and does not replace the supported pull inbox.

For a Grok connection, the owner-only receiver enrollment endpoint accepts `native_target` as the saved Grok Bot webhook POST URL and `grok_webhook_key` as the routine's bearer key. The URL must use HTTPS on `api2.cursor.sh`, `cursor.com`, or a `cursor.com` subdomain, with no URL credentials, fragment, or nonstandard port. AgentWay encrypts both values in its vault and never returns them in status, event streams, attempt history or logs. Enrollment rotates the receiver binding generation and receiver token, clears prior native verification, and removes any old webhook config. Disabling the binding removes its config and blocks outstanding deliveries. The owner must configure the routine in the **intended** Bot separately; enrollment does not create or edit a Grok routine.

The dispatch worker only selects an unexpired outbox delivery when its Grok binding is already verified, enabled, current and configured, and the directed grant is still present. It persists an attempt before sending a short JSON envelope with delivery/task IDs, kind, generation and deadline. It does not send task instructions or AgentWay credentials. A provider HTTP 200 records transport admission with no invented native run ID. Another HTTP status is retryable only within the existing three-attempt bound because [Cursor documents that non-200 means no run started](https://prod.cursor.com/help/grok-bot/routines). A lost response is an unknown outcome and blocks retry until a native run is reconciled. The Bot still has to authenticate to AgentWay, claim the task, and submit its result; the original sender still has to receive and acknowledge that result. The same routine may receive `task_offered` and `result_available`, but its instructions must handle both explicitly.

No product can become verified through this enrollment or a successful webhook response. A live harmless idle-to-idle test of the exact Bot and original sender, with native run history and restart/revocation recovery, remains the release gate. There is no UI or production verification route in this slice. Do not present the adapter as a working automatic handoff until those tests pass.
