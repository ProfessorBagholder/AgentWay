# Handoff delivery foundation

Status: implemented on the test branch, 2026-09-24 UTC. This is durable storage and fail-closed eligibility for a future automatic receiver path. It does **not** dispatch, wake a native agent, provision a binding, or prove delivery.

Migration `0021_handoff_delivery_foundation.sql` adds per-connection receiver bindings and a delivery outbox. A binding records the product, encrypted target reference, receiver credential hash, generation, enablement, and proof window. There is intentionally no enrollment or verification route yet: a connector credential does not prove that a particular existing conversation can receive work. Existing handoffs migrate to `delivery_mode=pull`, retaining their rowid cursors, receipts, events and task semantics.

Task creation accepts an optional `automatic_delivery` flag. It defaults to false and preserves the existing inbox. When true, both the sender and recipient must have enabled, unexpired verified bindings, the directed grant must exist, and both connections must be active. The server pins both binding generations. It writes the task, history event and recipient `task_offered` outbox entry in one transaction; an outbox failure rolls back the task and event. Completion, failure, cancellation and timeout append one `result_available` entry for the original sender in the same transaction as the terminal task event. The result entry has a separate seven-day deadline. Outbox entries contain IDs, kind, connection, binding generation and scheduling fields, but no task instructions or secret.

The table reserves pending, admitted, delivered, blocked and expired transport states. None of those states is currently advanced by a dispatcher, and no binding can be verified through the shipped API. Consequently an ordinary installation cannot create an automatic task yet. The API fails closed with `Automatic handoff receiver is unavailable`; it never relabels a pull task as delivered. The new input field is a forward-compatible opt-in contract, not an advertised native capability.

Before enabling this path, implement owner-approved binding enrollment with encrypted target and receiver-scoped secret handling; a versioned receiver delivery/admission API; a restart-safe dispatcher with bounded retries, generation and grant checks, and terminal expiry; native adapters that reach the exact bound agent; and authenticated sender return receipt. The same conformance suite must pass for every advertised agent product. No manual database insertion is a substitute for verification in production.
