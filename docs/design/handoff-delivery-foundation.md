# Handoff delivery foundation

Status: foundation merged in PR19; isolated transport conformance added on `feat/handoff-receiver-conformance`, 2026-09-24 UTC. Durable storage, separate receiver transport identity and fail-closed task eligibility exist. There is **no automatic dispatcher, production binding verification or complete unattended two-way handoff proof**. The common pull inbox has an optional SSE hint stream, but it is separate from this automatic receiver outbox.

Migration `0021_handoff_delivery_foundation.sql` adds per-connection receiver bindings and a delivery outbox. A binding stores product, encrypted native target reference, hashed receiver credential, generation, enablement and proof window. Existing handoffs migrate to `delivery_mode=pull`, retaining rowid cursors, receipts, events and task semantics. No connection is marked verified by migration or enrollment.

The loopback owner API can enroll or rotate a candidate binding with `POST /api/handoff-receivers/{connection_id}` and `{"native_target":"opaque native target"}`. It returns a high-entropy receiver token **once**; the database stores only its hash. `GET` returns status without target or secret. `DELETE` disables the binding. Rotation increments the generation, invalidates the previous token and blocks unresolved old-generation deliveries. Enrollment leaves `ready=false` because a connection credential or transport registration cannot prove delivery to an existing native conversation. This API is an integration preview, not a user-facing setup flow; target selection and native proof must be supplied by a supported product adapter before release.

The public machine listener accepts the receiver token only on `GET /v1/handoff-receiver/deliveries` and `POST /v1/handoff-receiver/deliveries/{id}/admit`; it does not grant agent task, MCP or publishing access. Conversely, an agent token cannot call the receiver feed. The paginated feed contains protocol version, delivery ID, kind, task ID, binding generation and deadline, with no instructions, result or credential. An adapter's admission includes its generation and an opaque native reference, stored encrypted. Admission is idempotent for the same reference and does **not** accept the task for the native agent. The native agent must still claim the task using its own connection credential **and the admitted delivery ID**. The original sender likewise acknowledges a returned result with the admitted return-delivery ID. Wrong connection, stale generation, expired offer and revoked grant are fenced. A background sweep terminates expired pending records as `expired` and admitted records as `blocked` with `native_outcome_unknown`; it does not retry an uncertain native action. There is no dispatcher or event stream for this automatic receiver outbox. The separate [pull-task SSE hint stream](handoff-task-stream.md) does not admit outbox envelopes or establish a verified native receiver binding; polling this feed alone is not handoff readiness.

Task creation accepts optional `automatic_delivery`, default false. True requires both agents to have enabled, unexpired **verified** bindings, an owner grant and active connections. It pins both generations and commits task, audit event and `task_offered` outbox entry atomically. Completion, failure, cancellation and timeout commit one `result_available` entry for the original sender with a separate seven-day deadline. An authenticated recipient claim presenting the admitted offer ID marks the offer delivered; a manual claim without admission blocks the offer with a diagnostic instead of inventing transport proof. An authenticated sender result acknowledgment presenting the admitted return ID marks the return delivered; acknowledgment without admission blocks it as manually received. Grant revocation fences automatic claims and blocks outstanding offers. Pull-mode behavior remains unchanged.

No production API can mark a candidate binding verified yet. Ordinary automatic requests therefore fail closed with `Automatic handoff receiver is unavailable`, and no real delivery is attempted. Before enabling the mode, add finite harmless native probes that verify both directions to the **exact** bound conversations, binding proof expiry/reverification, an owner-facing setup and recovery flow, durable bounded dispatch or long-poll supervision, transport-attempt history, cancellation and owner recovery from expired or uncertain delivery, and product adapters. Run the same conformance suite for every advertised agent product. A mock, token exchange or manually inserted proof is not release evidence.

The isolated `prototypes/handoff_receiver/transport_conformance.py` harness marks only its disposable bindings verified through direct test-database writes. It checks the actual HTTP offer/admit/claim/return/ack path across a server restart, credential isolation, admission replay, and grant revocation. This is an infrastructure regression test, not a production verification route or a product-native conformance pass.
